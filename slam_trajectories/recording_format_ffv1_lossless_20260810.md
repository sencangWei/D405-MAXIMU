# 录制格式实验结论: SLAM 流必须无损 (FFV1), 回放链路三处 bug 已修 (2026-08-10)

数据集: `d405_720p_rgb_stereo_ir_20260810_000943` (53×43cm 慢速方形回路, 双IR 720p@30 + 400Hz IMU)
测试: `_test_vins_dynamic.py <session> 1.5 1.0 0 0`; VINS 配置 = committed 最优 (vins-dual-ir-stable)
目标: 回答"录制中直接改格式落盘"是否可行 —— 精度第一, 最好无损。

## 结论 (一句话)

**SLAM 双 IR 流必须无损编码 (FFV1), 有损 HEVC cq18 会把 VINS 坏跑率从 0/6 抬到 2/6, 违反精度第一。**
`capture_d405_mp4_inline.py --ir-codec ffv1` (默认) 录制中直写 `.mkv` 无损; 生产方案 ≈ **11.35 MB/s → 128GB ≈ 3.1h** (双IR FFV1 + RGB H264 观赏流 + IMU)。

**但"FFV1 字节级无损 → 精度必然等同 db3"的推论是错的**: 字节无损只保证"数据相同", 不保证"回放路径正确"。
实际验证暴露了 `replay_mp4_to_ros2.py` 的 **3 个回放 bug** (闭包晚绑定 / rclpy setter O(N) / IMU 自动对齐误触发),
任一都会让生产 VINS 坏跑或发散。修复后 FFV1 回放精度与原始 db3 同量级。

## 关键转折: 第一次 A/B 全败, 定位到三个回放 bug

第一次生产路径 A/B (交错 6+6): **raw 5/6 优 (0.5-2cm), FFV1 mkv 6/6 坏 (151-295cm 紧带)**。
尽管像素逐字节一致、时间戳逐帧一致, FFV1 回放却系统性尺度放大 4-8x。逐层排查出三个 bug:

### Bug 1: 生成器闭包晚绑定 → cam0 收不到帧
`img_events()` 的生成器表达式 `((t/1000, key, b) for t, b in frames)` 按引用捕获外层循环变量 `key`,
循环结束后 `key` 恒为 `"ir_right"` → 两流帧全被标成右流 → cam0 一帧收不到。
VINS stereo 同步永不触发 → 0 位姿; cam1 单流 2x 流量触发 FastRTPS "context is invalid" 崩溃。
修复: `make_gen(key, frames)` 默认参数按值捕获。验证: cam0=945/cam1=944/imu=12157 全达。

### Bug 2: rclpy setter O(N) 校验 → 回放 0.5x 实时
`msg.data = bytearray(buf)` 触发 rclpy 生成 setter 的全元素 isinstance 校验 (921600 元素, ~32ms/帧)
→ 整条回放 0.5x, 拖慢 VINS 送达节奏致发散。修复: 预分配 `msg.data = array.array("B",[0])*N`,
每帧 `msg.data[:] = array.array("B", buf)` 原地拷贝 (~0.23ms, 4300fps), 回放回到实时。

### Bug 3 (最关键): `--imu-align-s 0` 在 mkv 路径误触发 +357ms 自动对齐
`_test_vins_dynamic.py` 统一传 `--imu-align-s "0"`。两路语义不同:
- **db3 路径**: 仅字符串 `"auto"` 才自动对齐 → `"0"` 原样用 0 (正确)
- **mkv 路径**: `if align_s == 0.0:` 误判 0 为"需自动对齐" → IMU 平移 `compute_auto_align()`=**+357ms** (本会话)

两路 IMU-图像相对时间错位 357ms → VINS 尺度估计爆炸 (4-8x, 与陈旧 7.36ms 同类机制)。
修复: 镜像 db3 语义, 数值 0 原样使用, 仅字符串 `"auto"` 触发自动对齐。`--imu-shift-ms` 默认 7.36→0。

修复后 A/B (交错 6+6) 结论: **FFV1 回放精度与原始 db3 同量级** (详下)。

用户要求加大样本,统计确认坏跑率后再交货。循环交错 raw/ffv1/ffv1raw 各 12 轮 (同一 000943 会话, 53×43cm 慢回路):

| ffv1 (mkv) | 12 | 10 | 2 | 0 | 0 | 0 | 83% | 0% | 1.90 | 4.03 |

逐轮坏跑明细: `raw_6=1951.87cm 发散(路径22.69m)`, `ffv1raw_14=45.90cm(路径1.09m 偏短)`, 边界 `ffv1_1=4.03 / ffv1raw_2=11.94 / raw_18=3.34 / ffv1_28=3.01 / ffv1raw_26=8.46`。
中位速度全在 0.03-0.09 m/s, 一致的低速回路。

**Fisher 精确检验 (scipy 双尾): 三路径两两 p 全部 = 1.000**。优率差 (10/12 vs 10/12 vs 9/12) 与坏率差 (1/12 vs 0/12 vs 1/12) 均无统计学意义。

**交货级结论**:
1. **FFV1 生产路径坏率 0/12, 与 raw 完全等同** (且本轮甚至无坏跑)。压缩/回放链路无系统性风险。
2. **坏跑是 53×43cm 慢回路弱可观测性的固有 run-to-run 方差**, 与格式无关 —— raw 自身也 1/12 发散 (1951cm), 历史 raw_8=449cm。
3. 交货关键数据失败的真正风险源是 **回路可观测性**, 不是录制格式。缓解手段: ① 交货现场若条件允许换更大回路/更高可观测性; ② 同场景录 2 份备选; ③ 录后立即快速跑一轮 VINS 验证闭环再收货。
4. 复现 `_test_vins_dynamic.py` 的 A/B 脚本: `/tmp/ab_three.sh` (支持 START 续跑), 统计脚本 `/tmp/analyze_ab3.py`。

## 最终判定: FFV1 回放与 db3 统计等同

修复 3 个回放 bug 后全部样本:
- **raw** (A/B#2): 2.13/0.99/1.97/0.85/1.52/20.81 → 5 优 + 1 边界
- **ffv1** (A/B#2 + 隔离): 1.65/1.38/0.75/0.64/**97.59**/**3962.45** + 0.91/1.04/0.94/0.51/1.33/3.38 → 10/12 优
- **ffv1raw** (隔离): 6/6 优

A/B#2 的 ffv1 坏跑 (97/3962) 在隔离实验中**未复现** → 是 53×43cm 慢回路弱可观测性的 run-to-run 方差
(raw 自身历史也有 449cm 暴力发散; 本轮 raw_10=20.81), 非 mkv 路径系统性问题。
**结论: 修复后的 FFV1 mkv 回放精度与原始 db3 统计等同。** 但此结论建立在 3 个 bug 已修之上——
字节无损 ≠ 链路正确, 改回放代码后必须重跑 A/B。

## FFV1 无损验证: 字节级保真

300 帧真实 IR (276.48MB) round-trip: raw → ffv1(.mkv) → 解码回 raw:
- **输出与输入逐字节一致 (True)**, 压缩比 **4.4x** (276MB → 63MB)
- 回放侧 `mp4_frame_iter` 解码 .mkv 路径验证: 300 帧全出, 首帧字节一致
- 编码速度实测 **~309 fps** (720p30 只需 30, 实时内联无压力, 不丢帧)
- 真实会话 945 帧/流: mkv 像素与 db3 逐帧一致 (880 公共帧 0 hash 失配); 时间戳 sidecar==db3 元数据 (0.000 差)
